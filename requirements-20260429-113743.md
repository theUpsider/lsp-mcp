## Summary

Ein MCP-Server, der Sprachmodellen Zugriff auf Language-Server-Protocol-Funktionalität gibt. Im Gegensatz zu existierenden LSP-MCP-Servern auf GitHub unterstützt dieser Server alle gängigen Programmiersprachen (Python, C#, TypeScript, JavaScript, Java, Go, Rust, C, C++, Ruby, PHP, Kotlin, Swift) ohne manuelle Pro-Sprache-Konfiguration. Der Server erkennt automatisch, welche Sprache und welcher Language Server für die jeweilige Codebase passend sind, installiert fehlende Language Server selbstständig und exponiert alle LSP-Operationen — lesend und schreibend — unter einer stabilen, sprachunabhängigen Tool-Signatur. Das Projekt wird als npm-Paket **`@theupsider/lsp-mcp`** veröffentlicht und über eine GitHub-Actions-Pipeline gebaut, getestet und released.

Der MCP-Server **discovered automatisch** existierende LSP-Konfigurationsdateien (`tsconfig.json`, `pyrightconfig.json`, `.pylintrc`, etc.) im Projekt-Root und übergibt sie an die LSP-Server. | REQ-20260429-113743-008 | Stabile Tool-Signaturen             | Die Signaturen (Name, Parameter, Rückgabetypen) der vom MCP-Server angebotenen Tools müssen über alle Sprachen und Language-Server-Implementierungen hinweg identisch bleiben. Eine Sprachänderung in der Codebase darf die Tool-Schnittstelle nicht verändern. Alle Tools verwenden ein **gemeinsames Basis-Parameter-Schema** mit optionalen Feldern (`file`, `line`, `character`, `query`, `newName`, `includeDeclaration`, `options`). Jedes Tool definiert in seiner Beschreibung explizit, welche Felder required sind.                                                                                                                  |
| REQ-20260429-113743-009 | Codebase-bezogener Kontext          | Das System verwaltet einen **einzigen aktiven Projekt-Root** pro Server-Instanz. Der Root wird **dynamisch** über das Tool `lsp_init` gesetzt (siehe REQ-20260429-113743-039). Wenn kein `lsp_init`-Aufruf vorliegt, startet der Server im Zustand `waiting-for-init`. Alle MCP-Tools außer `lsp_init` geben einen strukturierten Fehler zurück, wenn kein Root gesetzt ist. Ein Wechsel des Roots erfordert keinen Neustart — ein erneuter `lsp_init`-Aufruf fährt den alten LifecycleManager herunter und startet einen neuen.                                                                                                                                                                                                                                                                                                                                                                     |
| REQ-20260429-113743-039 | lsp_init Tool & Tool-Sichtbarkeit   | Das System muss ein Setup-Tool `lsp_init` bereitstellen, das den aktiven Projekt-Root setzt. Parameter: `root` (string, required, absoluter Pfad). Das Tool validiert, dass `root` ein existierendes Verzeichnis ist. Nach erfolgreichem Aufruf: (1) wird der alte LifecycleManager heruntergefahren (falls vorhanden), (2) ein neuer LifecycleManager für den neuen Root gestartet, (3) eine `notifications/tools/list_changed`-Notification an den MCP-Client gesendet. **Tool-Sichtbarkeit**: `lsp_init` erscheint in der Tool-Liste **nur** solange kein Root gesetzt ist (Server im Zustand `waiting-for-init`). Nach erfolgreichem `lsp_init`-Aufruf wird das Tool aus der Liste entfernt — das Modell sieht es nicht mehr. Der Server merkt sich den gesetzten Root für die gesamte Restlaufzeit. Folgeaufrufe von `lsp_init` während der Root bereits gesetzt ist, geben zurück: "Already initialized. Root is set to /path. Restart server to change root." Das `lsp_init`-Tool ist **kein** reguläres LSP-Tool und erscheint nicht in REQ-010. |

| REQ-20260429-113743-011 | Schreibende LSP-Tools               | Das System muss folgende schreibenden LSP-Operationen als **explizite MCP-Tools** exponieren: `lsp_rename`, `lsp_code_action`, `lsp_formatting`, `lsp_range_formatting`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| REQ-20260429-113743-023 | Hybrid-Rückgabewerte                | Jede MCP-Tool-Response muss ein **hybrides Format** verwenden: ein lesbares `text`-Feld mit einer menschlich lesbaren Zusammenfassung der LSP-Antwort (Hauptfeld für das Sprachmodell) und ein `raw`-Feld mit den unveränderten rohen LSP-Daten als Backup.                                                                                                                                                                                                                                                                                                                                                                                    |
| REQ-20260429-113743-024 | workspace_symbols Limiting          | Das Tool `lsp_workspace_symbols` verwendet ein **query-basiertes Limit**: Bei leerem `query`-Parameter (Default: `""`) werden maximal **100 Ergebnisse** zurückgegeben. Bei einem spezifischen Query werden bis zu **500 Ergebnisse** zurückgegeben. Die Ergebnisse werden im `text`-Feld kompakt als Markdown-Liste formatiert.                                                                                                                                                                                                                                                                                                               |
| REQ-20260429-113743-025 | Diagnostics Scoping                 | Das Tool `lsp_diagnostics` hat einen optionalen `scope`-Parameter: `"file"` (Default, benötigt `file`-Parameter) für file-scoped Diagnostics oder `"workspace"` (optional mit `language`-Filter) für repository-weite Diagnostics. Workspace-wide hat ein Hard-Limit von **200 Diagnostics**, sortiert nach Schweregrad (errors vor warnings).                                                                                                                                                                                                                                                                                                 |
| REQ-20260429-113743-026 | Code Action Workflow                | Das Tool `lsp_code_action` hat einen optionalen `apply`-Parameter (Default: `false`). Falls die gewählte Action ein `WorkspaceEdit` enthält, wird dieses direkt angewendet.                                                                                                                                                                                                                                                                                           |
| REQ-20260429-113743-027 | File Path / URI Konvertierung       | Der MCP-Server akzeptiert **file paths** als Parameter (z.B. `/home/user/project/src/main.py`) und konvertiert **automatisch** zu LSP file URIs (`file:///home/user/project/src/main.py`). Der Nutzer muss sich nicht mit LSP-URIs auseinandersetzen.                                                                                                                                                                                                                                                        |
| REQ-20260429-113743-028 | Health-Check Tool                   | Das System muss ein lesendes `lsp_health`-Tool expose, das den aktuellen Status aller LSP-Server zurückgibt: erkannte Sprachen, Server-Status (ready/error/restarting), und Fehlermeldungen. | REQ-20260429-113743-029 | LSP-Fehlerbehandlung                | LSP-Fehler werden im **hybriden Format** zurückgegeben: ein `error: true` Flag, ein menschenlesbarer `text`-Fehler (z.B. | REQ-20260429-113743-031 | Kein Caching                        | Der MCP-Server verwendet **kein Caching** von LSP-Antworten. | REQ-20260429-113743-034 | Per-Request Timeouts                | Verschiedene Operationen haben **operation-spezifische Timeouts**: `definition`, `type_definition`, `implementation` → **5 Sekunden**; `references`, `document_symbols` → **15 Sekunden**; `workspace_symbols`, `diagnostics` (workspace) → **30 Sekunden**. Jeder Timeout wird geloggt (REQ-018).                                                                                                                                                                      |
| REQ-20260429-113743-035 | File Writing                        | Schreibende Operationen (`lsp_code_action`, `lsp_rename`, `lsp_formatting`) wenden den Edit über den LSP an, schreiben die Änderungen **direkt auf die Festplatte** und senden `textDocument/didSave` an den LSP. | REQ-20260429-113743-036 | Rename Support Check                | Das Tool `lsp_rename` prüft vor der Ausführung, ob der LSP Rename unterstützt (via `serverCapabilities.renameProvider`). | REQ-20260429-113743-037 | CLI-Interface                       | Der Server ist ein **Stdio-Server** (LSP/MCP-konform): er liest von stdin und schreibt nach stdout. Optional: `lsp-mcp --version` zeigt die Paketversion. Kein Flag, keine Subcommands für den Hauptbetrieb.                                                                                                                                                                                                                                      |
| REQ-20260429-113743-038 | Graceful Shutdown                   | Bei Disconnect sendet der Server `exit` an alle LSP-Server und wartet max. **5 Sekunden**. Verbleibende LSP-Server werden mit `SIGKILL` beendet. Der Server loggt beim Shutdown einen Report: "Shutdown: X LSP-Server beendet, Y Fehler."                                                                                                                                                                                                                                                                                                                                                                                                      |
| REQ-20260429-113743-012 | Lifecycle-Management                | Alle erkannten Language Server starten **nach `lsp_init`** (keep-alive) und laufen permanent während der Server-Laufzeit. Der Server überwacht die LSP-Prozesse auf Health (periodische Ping-Checks) und startet fehlgeschlagene Server automatisch neu. Bei Inaktivität werden LSP-Server **nicht** beendet. Beim Init erfolgt ein **Scan-then-start**: der Projekt-Root wird gescannt, alle Sprachen erkannt, alle LSP-Server gestartet. Ein **Timeout von 30 Sekunden** verhindert endloses Warten. Nach dem Timeout ist der Server trotzdem nutzbar — für Sprachen, deren LSP nicht bereit ist, gibt es strukturierte Fehler (REQ-014). |
| REQ-20260429-113743-013 | Mehrere parallele Sprachen          | Das System muss in einem Polyglot-Projekt mehrere Language Server gleichzeitig betreiben können (z.B. TypeScript + Python im selben Repository). Die Datei-zu-LSP-Zuordnung erfolgt **hybrid**: primär projekt-root-basiert (Dateien innerhalb eines erkannten Projekt-Roots gehen an den dortigen LSP), mit **dateiendung-basierter Zuordnung** als Fallback für Dateien außerhalb von Projekt-Roots. Dateien ohne Zuordnung werden ignoriert.                                                                                                                                                                                                |
| REQ-20260429-113743-014 | Fallback bei fehlendem LSP          | Wenn für eine erkannte Sprache kein Language Server verfügbar ist und die automatische Installation fehlschlägt, muss das System einen klaren, strukturierten Fehler mit Installationshinweis an das Modell zurückgeben, ohne zu crashen.                                                                                                                                                                                                                                                                                                                                                                                                      |

### Language Server Mapping Reference

Die folgende Tabelle definiert die hardcoded Mapping-Tabelle (REQ-005). Sie ist die autoritative Quelle für Sprache → Language Server.

| Sprache    | Präferenz 1 (Server-Package)                    | Präferenz 2 (Fallback)      | Paketmanager         |
| ---------- | ----------------------------------------------- | --------------------------- | -------------------- |
| Python     | `pyright` (`pyright-langserver`)                | `python-lsp-server` (pylsp) | npm / pip            |
| TypeScript | `typescript-language-server`                    | —                           | npm                  |
| JavaScript | `typescript-language-server`                    | —                           | npm                  |
| C#         | `omnisharp-roslyn` (`omnisharp`)                | —                           | dotnet tool          |
| Java       | `vscode-java` (`java-language-server`)          | `eclipse-jdtls`             | npm / apt            |
| Go         | `gopls`                                         | —                           | go install           |
| Rust       | `rust-analyzer`                                 | —                           | cargo install        |
| C          | `clangd`                                        | —                           | apt / brew           |
| C++        | `clangd`                                        | —                           | apt / brew           |
| Ruby       | `solargraph`                                    | —                           | gem                  |
| PHP        | `intelephense` (`intelephense-language-server`) | —                           | npm                  |
| Kotlin     | `kotlin-language-server`                        | —                           | npm                  |
| Swift      | `sourcekit-lsp`                                 | —                           | brew / swift package |

**Hinweise:**

- TypeScript und JavaScript teilen sich `typescript-language-server` (ein Server für beide).
- C und C++ teilen sich `clangd` (ein Server für beide).
- Die Präferenz-1-Server werden zuerst versucht. Nur wenn sie nicht gefunden werden, wird Präferenz-2 geprüft.
- Wenn beide scheitern, erfolgt user-local Installation (REQ-006).
