## Summary

Ein MCP-Server, der Sprachmodellen Zugriff auf Language-Server-Protocol-Funktionalität gibt. Im Gegensatz zu existierenden LSP-MCP-Servern auf GitHub unterstützt dieser Server alle gängigen Programmiersprachen (Python, C#, TypeScript, JavaScript, Java, Go, Rust, C, C++, Ruby, PHP, Kotlin, Swift) ohne manuelle Pro-Sprache-Konfiguration. Der Server erkennt automatisch, welche Sprache und welcher Language Server für die jeweilige Codebase passend sind, installiert fehlende Language Server selbstständig und exponiert alle LSP-Operationen — lesend und schreibend — unter einer stabilen, sprachunabhängigen Tool-Signatur. Das Projekt wird als npm-Paket veröffentlicht und über eine GitHub-Actions-Pipeline gebaut, getestet und released.

## Requirements

### Functional Requirements

| ID | Title | Description |
|----|-------|-------------|
| REQ-20260429-113743-001 | MCP-Server-Bereitstellung | Das System muss als MCP-Server implementiert sein, der von Sprachmodellen über das MCP-Protokoll angesprochen werden kann. |
| REQ-20260429-113743-002 | LSP-Client-Funktion | Das System muss als Language-Server-Protocol-Client agieren und mit beliebigen LSP-konformen Servern kommunizieren können. |
| REQ-20260429-113743-003 | Multi-Sprach-Unterstützung | Das System muss out-of-the-box folgende Sprachen unterstützen (abschließende Liste): Python, C#, TypeScript, JavaScript, Java, Go, Rust, C, C++, Ruby, PHP, Kotlin, Swift. |
| REQ-20260429-113743-004 | Automatische Sprach-Erkennung | Das System muss die Programmiersprache(n) einer Codebase automatisch anhand von Dateiendungen und Projekt-Markern erkennen. Unterstützte Marker umfassen mindestens: `package.json`, `tsconfig.json`, `pyproject.toml`, `setup.py`, `*.csproj`, `*.sln`, `Cargo.toml`, `go.mod`, `pom.xml`, `build.gradle`, `Gemfile`, `composer.json`, `Package.swift`. |
| REQ-20260429-113743-005 | Automatische LSP-Auswahl | Das System muss basierend auf der erkannten Sprache automatisch den passenden Language Server auswählen und starten, ohne Nutzereingriff. |
| REQ-20260429-113743-006 | Automatische LSP-Installation | Wenn ein benötigter Language Server nicht auf dem System vorhanden ist, muss das System ihn automatisch über den plattformüblichen Paketmanager installieren (z.B. npm für `typescript-language-server`, pip für `python-lsp-server`, `dotnet tool` für OmniSharp, etc.) und den Nutzer via strukturiertem Log darüber informieren. |
| REQ-20260429-113743-007 | Keine manuelle Sprach-Konfiguration | Der Nutzer darf nicht gezwungen sein, einzelne Sprachen oder Language Server manuell zu konfigurieren, um die Grundfunktionalität zu nutzen. |
| REQ-20260429-113743-008 | Stabile Tool-Signaturen | Die Signaturen (Name, Parameter, Rückgabetypen) der vom MCP-Server angebotenen Tools müssen über alle Sprachen und Language-Server-Implementierungen hinweg identisch bleiben. Eine Sprachänderung in der Codebase darf die Tool-Schnittstelle nicht verändern. |
| REQ-20260429-113743-009 | Codebase-bezogener Kontext | Das System muss pro Codebase (Projekt-Root / Working Directory) einen isolierten LSP-Kontext verwalten, sodass das Sprachmodell Code-Operationen projektspezifisch ausführen kann. |
| REQ-20260429-113743-010 | Lesende LSP-Tools | Das System muss folgende lesenden LSP-Operationen als MCP-Tools exponieren: `hover`, `definition`, `references`, `document_symbols`, `workspace_symbols`, `completion`, `diagnostics`, `signature_help`, `type_definition`, `implementation`. |
| REQ-20260429-113743-011 | Schreibende LSP-Tools | Das System muss folgende schreibenden LSP-Operationen als MCP-Tools exponieren: `rename`, `code_action`, `formatting`, `range_formatting`, `apply_workspace_edit`. |
| REQ-20260429-113743-012 | Lifecycle-Management | Das System muss Language-Server-Prozesse automatisch starten, überwachen und bei Inaktivität oder Fehler kontrolliert beenden bzw. neu starten. |
| REQ-20260429-113743-013 | Mehrere parallele Sprachen | Das System muss in einem Polyglot-Projekt mehrere Language Server gleichzeitig betreiben können (z.B. TypeScript + Python im selben Repository). |
| REQ-20260429-113743-014 | Fallback bei fehlendem LSP | Wenn für eine erkannte Sprache kein Language Server verfügbar ist und die automatische Installation fehlschlägt, muss das System einen klaren, strukturierten Fehler mit Installationshinweis an das Modell zurückgeben, ohne zu crashen. |

### Non-Functional Requirements

| ID | Title | Description |
|----|-------|-------------|
| REQ-20260429-113743-015 | Zero-Config-Installation | Nach `npm install -g <paketname>` bzw. `bunx <paketname>` muss der Server ohne weitere Konfigurationsschritte funktionsfähig sein. |
| REQ-20260429-113743-016 | Plattform-Unterstützung | Das System muss auf Linux (x64, arm64), macOS (x64, Apple Silicon) und Windows (x64) lauffähig sein. |
| REQ-20260429-113743-017 | Performance des MCP-Layers | LSP-Anfragen, die der zugrunde liegende Language Server in unter 500 ms beantwortet, dürfen durch das MCP-Layer nicht um mehr als 100 ms zusätzliche Latenz verzögert werden. |
| REQ-20260429-113743-018 | Strukturiertes Logging | Das System muss strukturierte Logs im JSON-Format für LSP-Aufrufe, Fehler, Installations-Events und Lifecycle-Events bereitstellen. Log-Output darf ausschließlich auf stderr erfolgen, um den MCP-Stdio-Kanal (stdout) nicht zu verschmutzen. |
| REQ-20260429-113743-019 | Unit-Test-Abdeckung | Das Projekt muss eine automatisierte Unit-Testsuite besitzen, die mindestens die Module Sprach-Erkennung, LSP-Adapter und Tool-Mapping abdeckt. Die Mindest-Coverage beträgt 80%. |
| REQ-20260429-113743-020 | Integrationstests | Für jede in REQ-20260429-113743-003 genannte Sprache muss mindestens ein Integrationstest existieren, der eine Minimal-Codebase lädt und einen LSP-Aufruf (lesend und schreibend) vollständig über den MCP-Server ausführt und das Ergebnis validiert. |
| REQ-20260429-113743-021 | Dokumentation | Das Projekt muss ein README mit folgenden Abschnitten enthalten: Installation (npm & bun), Quickstart, vollständige Tool-Referenz (Parameter & Rückgaben), Liste der unterstützten Sprachen mit zugehörigem Language Server, Troubleshooting für fehlgeschlagene Auto-Installation. |

- Docker-Image, statische Binaries oder andere Distributionsformate außer npm.
